# オプション・設定値の削除／変更時の検証

前回は追加を中心に確認しており、削除・縮小・変更の検証は不足していた。今回は定義を一時的に変更する回帰テストを追加した。実際に公開するオプション・設定値の削除や名称変更は行っていない。

## 確認結果

| 変更の試験 | 期待される動作・必要な対応 | 確認結果 |
| --- | --- | --- |
| 35オプションを1件ずつ削除 | 無関係なコマンドの共通検証が壊れない | 当初10項目の削除でKeyError/AttributeError。任意項目の残存参照を修正後、全35項目で実行境界まで検証通過 |
| 削除したオプションを前・途中・後に指定 | 旧名を未知オプションとして終了2にする。ヘルプからも消える | 全105配置で一致。`--json` 自体を削除した場合も通常のstderr診断になる |
| 画像形式、検査レベル、fallbackの選択肢を縮小 | 旧値は `argument_error`、現在の選択肢だけを診断へ出す | テキスト/JSONと配置違いで一致。残る値は検証通過 |
| 排他相手のオプションを削除 | 残った指定が古い排他定義により拒否されない | 一致 |
| オプション名を変更 | 新名を診断に使用し、旧名を未知オプションとして拒否 | 解析・適用範囲の診断で一致。実行側・専用制約の参照も更新する必要がある |
| JSON指定の名称を変更し、後続に構文エラーを置く | 新しい出力指定を、解析完了前のエラーでも反映する | 固定の `--json` 判定を、登録された `json_output` flagの判定へ変更後、一致 |
| 適用範囲を縮小し、既定値も変更 | 新しい既定値をNamespaceへ設定し、非対応操作への明示指定を拒否 | 一致。設定・実行前に `option_scope` |
| オプションの型を変更 | 旧型の不正入力を安全に拒否する | 型変換の失敗は終了2、`argument_error / invalid_value`。新型の利用には専用検証・実行側の変更も必要 |
| 設定値の選択肢を削除・名称変更 | 旧値は項目を示す `configuration_error` にする | テキスト/JSONで一致。出典・行を保持し、失敗時はファイルを変更しない |
| 設定値の型・数値範囲を変更 | 以前の有効値が新しい条件に反する場合、項目・新条件を示す | 一致。整数→文字列、上下限の縮小を確認 |
| 選択肢を削除して旧既定値を残す | 不整合として開発時に検出する必要がある | argparse/Pydanticの既定値が自動では拒否されないことを再現。宣言済み既定値、設定既定値の再検証、同梱YAMLの契約テストを追加 |
| 設定項目を削除 | 現行の直接APIとYAML整理の違いを維持し、移行方針を決める | 直接モデル/API入力では拒否。user-managed YAMLでは検証前に旧静的項目を除外し、rewrite時に削除する既存仕様を確認 |
| 定義だけからオプションを削除し実行側参照を残す | 実行側参照も削除・更新する必要がある | 共通検証を通っても消費側でAttributeErrorになるケースを確認。実行成功とは扱わない |
| fallbackの `enabled` を `on` に変更し消費側を更新しない | 新値の意味を明示的に実装する必要がある | 解析は通過するが旧消費側はFalseとして扱う。名称の変更だけでは意味を移行できない |

35件の削除試験の有効入力は `doctor` の実行境界で停止している。全コマンドの処理内容や、削除の全組合せを網羅した検証ではない。引数不正・ヘルプでは設定解決・実行を禁止した。設定の書換え試験は一時ファイルだけで行った。プラグイン操作・ダウンロード・Cookie操作・外部通信は行っていない。

## 修正と互換性の境界

共通検証とJSON overrideの組立てが削除済みの任意項目を無条件に参照する箇所を修正した。JSONエラー出力の早期判定も、登録されたflagの保存先を参照する。現行の35オプションの公開動作は維持する。

契約照合では、CLIに許可する値がライブラリより少ないことを許容するようにした。消費側が持たない値をCLIが公開する場合は引き続き検出する。削除・変更に対応するには、定義だけでなく消費側、専用検証、既定値、同梱baseline、コメント付き雛形、利用例を一緒に更新する必要がある。

モデルの既定値だけを変更しても、同梱baselineの有効な旧値が優先される場合がある。既定値の妥当性チェックと、実際のlayer解決結果の確認は別である。

旧値は現在、自動変換されない。設定項目をモデルから削除すると既存の未知キー整理の対象になるため、実際の仕様変更前に「旧値を拒否する／明示的に移行する／非推奨期間を置く」方針を決める必要がある。今回、移行方式や未知キー整理の動作は変更していない。

## 検証記録

環境はWindows / Python 3.11.4。初回の削除・変更試験は15 failed / 160 passedで、共通検証・JSON判定の修正後は通過した。数値範囲の追加2件を含む削除・変更テストは177件、選択肢・既定値・同梱設定の契約照合は23件。
