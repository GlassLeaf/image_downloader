# 同期変換・専用ワーカー・WAT改修の実装と検証

実施日：2026-11-02。プラグインAPI番号はベータv3を維持し、画像変換フックを同期メソッドへ改訂した。

## 実装

- サイトのtransform_imageとprocessorのtransformを同期化。旧async宣言はロード時に拒否し、
  awaitableを返す同期関数も実行時に拒否する。通信・認証等の非同期フックは維持した。
- サービス所有のTransformExecutorを導入。既定2、設定可能範囲1〜4。サイトと全processorで共有し、
  投入前の実行枠取得、実行中ジョブの確定待ち、終了時の回収を管理する。
- 同一インスタンスへの並行呼出しとし、processor単位の直列化を除去した。contextvarsをコピーし、
  ログの所属を維持する。別イベントループからのExecutor再入は明示的に拒否する。
- ORIGINALの同一データ・Content-Typeに対する最終重複検証と、historyのみの変更による再エンコードを省いた。
  データ変更後の検証、全フレーム・MIME・画素数制限の処理は維持した。
- 外部プラグインは[作業コピー](optimized-plugin-a/README.md)と[差分](plugin-a-optimized.patch)を作成した。
  WATは純粋関数化し、ロック付き4項目・復号済みレコード16MiBのキャッシュへ変更した。
  可逆WebPと画素の復元順を維持し、出力MIME・拡張子を修正した。
- 同梱ソース、テンプレート、開発ツール、テスト、v3文書を移行した。同梱10パッケージは再署名済み。
  processor2個の署名鍵は既存サイト用ローカル鍵へ統一した。

元の外部プラグイン、実際のインストール先、信頼カタログは変更していない。
移行には[同期画像変換への移行](../../v3/maintenance/synchronous-image-transforms.md)を参照する。

## 検証

- 全体回帰試験：2,833 passed、23 skipped。実行中に確認した8失敗は、設定テンプレート、
  同期契約の期待値、実ユーザー設定を参照していたテストの分離を修正し、8件の再試験ですべて成功した。
- 専用Executor：上限1〜4、待機中キャンセル、開始済み処理の完了待ち、二重終了、contextvars、
  通常例外・SystemExit・KeyboardInterrupt、別loop再入、旧async拒否を検証した。
- WAT：改修前から固定した120件の変換テーブルと比較。回転・反転・端数寸法を含む。
  並行した画像復元を、WATを使わず作った参照画像の画素ハッシュとも照合した。
- 追加の検証・移行・開発ツール試験も成功。Ruff、mypy、wheel/sdistのビルドを確認した。

## 性能測定の方法

比較用ソースは改修前に `.runtime/transform-v3-baseline-20261102` へ保存した。
同じスナップショットに重複検証削減だけを適用したコピーも保存し、段階別の比較に使った。

| stage | 内容 |
| --- | --- |
| baseline | 改修前コア＋元の外部プラグイン、イベントループで直接変換 |
| dedup_only | baselineからORIGINALの最終重複検証だけを削減 |
| wat_dedup | dedup_only＋改修プラグインを直接実行。async変換を要求する旧コアへのラッパーは実験内だけで使用 |
| final1〜final4 | 改修後コア＋改修プラグイン、同一インスタンスを1〜4ワーカーで実行 |

- 768×1024の固定seed合成JPEG、回転・左右反転を含む48タイル/画像。
- ローカルHTTP → プラグイン変換 → コア検証 → 原子的保存までを測定。
- 8画像は0ms/100msの追加HTTP待ちを各5回、7段階の順を周回ごとにシャッフルして比較。
- 継続処理は32画像・100ms待ち・最終版1〜4ワーカーを各3回測定。
- 各試行は別プロセス。初回の画像ワーカー起動・検証を済ませてから測定し、画像生成・画素照合・終了処理は時間外。
- 親と画像ワーカープロセスのRSS合計を別スレッドから約20ms間隔で観測した。
  これはサンプリング値で、厳密な瞬間最大メモリではなく、共有ページが二重計上され得る。
- 測定中は回帰試験・ビルドを実行しない。CPU周波数やOSの他処理は固定していない。

再実行用ハーネスは `tools/benchmark_transform_pipeline.py`。RSS観測にpsutilを使用するが、
アプリ本体の依存関係には追加していない。旧比較用スナップショットは実装互換層として製品に組み込んでいない。

## 考察と制限

1. **既定2ワーカーは、8画像の総時間を改修前から34.3～35.6%短縮した。**
   直接実行時のheartbeat最大遅延の中央値は約4.6～5.3秒で、2ワーカーでは約56～58msになった。
   通信等を進められる応答性の改善も確認できた。

2. **小規模バッチで3→4を増やす追加効果は約1.8%に留まった。**
   観測RSSの中央値は2ワーカー約189～195MiB、3ワーカー約201～219MiB、4ワーカー約251MiB。
   4を一律の既定値にするより、2を保守的な既定値とし、処理量を優先する環境で3・4を選ぶ構成が妥当。
   実行間の時間範囲も重なっているため、小さな差に確定的な優劣を付けない。

3. **32画像では、1ワーカー30.49秒に対し2ワーカー18.73秒、3ワーカー15.70秒、4ワーカー14.89秒。**
   3→4の追加短縮は約5.2%。観測RSSの中央値は約159/194/220/244MiBで、8画像と同程度の範囲だった。
   観測終了時のRSSも約119～120MiBで揃った。枚数増加による単純な右肩上がりの保持はこの範囲では
   観測しなかったが、長時間実行のリーク非存在や瞬間最大値を証明するものではない。

4. **重複検証の削減だけの中央値差は約2～2.5%、WAT改修単独の追加高速化は確認できなかった。**
   可逆WebP圧縮を含む画像変換が支配的な条件で、主な時間短縮はスレッド実行から得られた。
   WAT改修は追記型メモリの廃止、共有状態の整理、キャッシュ上限の導入という安全性・保守性の改善が中心。
   データ件数や画像サイズによって寄与は変わり、各候補のCPU使用率を分離計測したわけではない。

5. **全82実行・944画像で、画素ハッシュと段階間の保存バイトハッシュが一致した。**
   出力形式やエンコーダー設定を変えて得た高速化ではない。MIME・拡張子・historyは意図した修正を含む。
   今回のデータから既定2を維持し、メモリと他処理への余力を見て3・4へ調整できる実装とした。

生データ・ソースSHA-256・環境情報は[implementation-results.json](implementation-results.json)に保存した。
例えば最終版2ワーカーの8画像条件は、次で再実行できる。

```powershell
python tools/benchmark_transform_pipeline.py --runtime-root . --plugin docs/investigations/plugin-thread-benchmark-2026-11-02/optimized-plugin-a --output .runtime/transform-v3-performance-recheck --stage final2 --workers 2 --images 8 --repeats 5 --delay 100
```

改修前との比較には、保存済みの `.runtime/transform-v3-baseline-20261102` をruntime-rootに指定し、
その中の `plugin-a-original` をpluginに指定して `--legacy-runtime` を付ける。
32画像は `--images 32 --repeats 3 --delay 100` で実行する。

画素数上限の既定値Noneは維持している。スレッド数の制限は、大きな単一画像のメモリ使用量を保証しない。
実行中のスレッドを強制停止する機構もないため、変換が停止すればキャンセル・サービス終了も待機し続け得る。
実サイト、認証、章一覧取得はこの性能測定に含めていない。実画像や大量章で同じ高速化率を保証するものではない。
