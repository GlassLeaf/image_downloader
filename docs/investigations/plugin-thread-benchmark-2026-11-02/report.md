# プラグイン画像変換のスレッド分離：模倣実験

実施日：2026-11-02。製品コードと指定された外部プラグインのソースは変更していない。

## 実験の範囲

指定された `C:/work/site_plugins/plugin_a/plugin.py` と `wat_module.py` を実際に読み込む。
サイトのinspect・認証・署名検証・章スケジューラー・ログ出力は省き、マニフェストを事前に生成する。
画像取得以降は、製品の `RequestGateway`、`PluginInvoker`、`ArtifactPipeline`、
`ImageProcessor`、`FileSystem.write_bytes_atomic` を使用する。

経路は、ローカルHTTP取得 → 指定プラグインの画像復元と可逆WebP圧縮 → コアの画像検証2回
（ORIGINAL、input_validation=both、追加processorなし）→ 原子的保存。
製品の重複検証・1プロセスの画像ワーカーもそのまま残し、変更要因を変換フックの実行場所に絞った。

HTTPサーバーは同一プロセス内の別スレッドで動かし、実TCPソケットを使う。
0ms/100msはサーバーが各応答前に追加する待ち時間であり、実測RTTや帯域制限ではない。
サーバーはクライアントのイベントループを使わないが、同じCPU資源は共有する。

## 比較する4方式

| 方式 | 実行場所と状態の所有 |
| --- | --- |
| direct | 現行同様、クライアントのイベントループでフックを直接await。1インスタンス共有 |
| thread1 | 専用1ワーカースレッドで実行。1インスタンス共有 |
| thread2_locked | 専用2ワーカースレッド。共有インスタンスをフック全体のロックで保護し、変換自体は直列 |
| thread2_isolated | 専用2ワーカースレッド。スレッドごとにインスタンスとWATキャッシュを所有し、同時変換可能 |

thread2_isolatedは、インスタンスの共有方法を変える追加の設計変更を伴う。
指定プラグインのこの変換処理には適用できたが、任意のプラグインへ互換性を保証する実験ではない。
共有インスタンスを無保護で複数スレッドへ渡す方式は試していない。

外部プラグインの非同期関数は現状内部にawaitがないため、ワーカー内でasyncio.runを使って実行した。
これは指定プラグインを動かす実験用アダプターであり、別loopへ依存する一般の非同期フックを
安全に移せることを意味しない。実行中ワーカーの完了を待ってからリソースを閉じる。

## 測定条件と正しさの確認

- Windows / Python 3.11 / Pillow 12.3.0、論理CPU 4。
- 入力768×1024、8画像、同時画像ジョブ上限8。4種類の固定seed合成画像をJPEG化して配信。
- placeholderは実WatModuleが解釈可能な48タイル/画像の形式。回転4方向・左右反転を含む。
- 復元画像は756×1008。実画像を使用していないため、圧縮負荷の代表性には限界がある。
- 各方式・遅延条件を3回ずつ。方式の実行順は各周回でシャッフル。
- コアのプロセス起動・初回検証を先に済ませる。合成データ生成、接続クライアント生成、
  最終の画素照合・リソース終了時間は総時間から除外する。各方式とも同じ境界を使う。
- 総時間にはHTTP取得、変換待ちと変換、コア検証、保存完了までを含む。
- 各実行の出力を読み直し、保存前後のSHA-256一致と、方式間の出力バイト一致を確認。
  加えて、WATを使わず独立に作ったタイル復元参照画像とデコード後のRGB画素ハッシュを照合。
- 10ms間隔のheartbeatが予定時刻からどれだけ遅れたかを測定。最大遅延を主な応答性指標とする。
  p95は停止中にサンプル自体を採れない影響を受けるため、単独では評価に用いない。

## 解釈と制限

単一スレッドへの移動では、重い画像変換そのものの直列実行は変わらない。
この条件では主な改善は通信などを進められる応答性であり、総時間の明確な短縮は確認できない。
共有インスタンスをロックした2スレッドも、変換能力を2倍にはしない。

インスタンスをワーカーごとに分けた2スレッドでは、Pillow等の処理が重なり、総時間の短縮が確認できた。
ただし、PythonのWAT処理だけがどれだけ並列化したか、GIL解放の各区間、CPU使用率、
ピークメモリは測っていない。追加キャッシュや同時画像展開によるメモリ増加も別途評価が必要。

fetch_mean_msとsave_mean_msは、await開始から再開までの時間を含む。
イベントループ停止による再開遅延が混ざるので、ネットワーク線上のRTTや物理ディスク時間ではない。
transform_mean_msは実行開始から終了まで、transform_queue_mean_msは投入から実行開始まで。
並列実行でCPUを取り合うと、1枚あたりの変換時間は増えても、全体時間は短くなり得る。

3回の小規模測定であり、CPU周波数、温度、OSスケジューリング、他アプリ等を固定していない。
実サイト、大量ページ、複数章、遅い保存先、他の画像形式、キャンセル障害試験は対象外。
この比率をそのまま本番全体の高速化率として扱わないこと。

```powershell
python tools/benchmark_plugin_threads.py --output .runtime/plugin-thread-benchmark --images 8 --width 768 --height 1024 --repeats 3 --delays 0 100 --modes direct thread1 thread2_locked thread2_isolated
```
