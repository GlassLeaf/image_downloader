# 画像変換ワーカーを最大4スレッドへ増やす比較実験

実施日：2026-11-02。前回の[実験の構成](report.md)を継続し、指定プラグインと製品コードは変更していない。

## 条件

- 前回と同じ、768×1024の合成JPEG8画像、48タイル/画像、回転・左右反転あり。
- 実HTTP取得、指定のプラグインによる変換、現行コアの検証2回、原子的保存までを測定。
- 追加HTTP待ち時間0ms/100ms、画像ジョブ上限8。出力はORIGINAL、追加processorなし。
- 直接実行、1・2・3・4スレッドを、各遅延条件で5回ずつ再測定する。前回の時間と今回の時間を混在させない。
- 2・3・4スレッドは各ワーカースレッドが専用のプラグインインスタンスとキャッシュを持つ。
  1スレッドは従来と同じ共有インスタンスを単一ワーカーで実行する。
- 各周回で実行順をシャッフル。画像生成とコアの初回プロセス起動は測定外。
- 変換フックの実行スレッド数と同時実行数も記録し、設定だけでなく並行実行を確認する。
- ここでいう4スレッドはプラグイン変換用の上限。HTTPサーバー、保存・検証待機用スレッド、
  コアの1画像ワーカープロセスなどを含めたシステム全体のスレッド数ではない。
- 出力を読み直して、保存前後・方式間のバイトハッシュ一致と、独立した復元処理との画素一致を確認。

再現コマンド：

```powershell
python tools/benchmark_plugin_threads.py --output .runtime/plugin-thread-benchmark-4workers --images 8 --width 768 --height 1024 --repeats 5 --delays 0 100 --modes direct thread1 thread2_isolated thread3_isolated thread4_isolated
```

## 考察

1. **4スレッドの中央値が最短で、現行比約1.89～1.94倍の処理速度になった。**
   時間短縮率は47.0～48.5%。2スレッドから4スレッドへの追加短縮は約15～16%であり、
   ワーカー数を2倍にしても処理時間が半分になる形ではない。

2. **2→3の効果より、3→4の効果は小さい。**
   総時間の中央値で2→3は10.6～11.9%短縮、3→4は4.0～5.8%短縮。
   ただし3・4スレッドの最小～最大範囲は重なっており、同じ周回で4が3より速かったのは
   遅延なしで2/5回、100ms条件で3/5回。周回を対応付けた短縮率の中央値はそれぞれ-0.6%、5.1%。
   4スレッドの優位が各回で安定して現れたとは評価できない。周回の対応も実行順の影響を完全には取り除かない。

3. **同時実行を増やすと、1枚あたりの変換時間は長くなった。**
   遅延なしの変換時間の中央値は、1スレッド約810ms、2スレッド約1,021ms、
   3スレッド約1,256ms、4スレッド約1,584ms。複数画像を重ねることで全体は速くなるが、
   個々の処理速度が向上しているわけではない。CPU資源の競合、Pythonで実行するWAT計算、
   コア検証が1プロセスに集約される構造などが伸びを制限する候補である。
   各候補の寄与は今回計測していない。

4. **応答性はスレッド分離で大幅に改善し、4スレッドでも秒単位の停止は観測しなかった。**
   各実行のheartbeat最大遅延の中央値は、直接実行約4.03～5.42秒に対して、
   2スレッド約28～30ms、3スレッド約43～48ms、4スレッド約36～57ms。
   4スレッドの100ms条件では単一実行に199msの最大遅延もあり、これらは最悪時の上限保証ではない。
   スレッド数増加で応答性が一貫して改善する傾向はなかった。

5. **製品ではワーカー数を設定可能にし、保守的な初期値は2、3・4を選べる構成を勧める。**
   今回のPCと画像で処理量を優先するなら4も候補だが、3に対する追加効果は小さい。
   日常利用で他処理への余力も残すなら2～3を比較して選ぶのが妥当。
   同時展開画像と複製キャッシュの増加があるため、4を一律既定にする判断にはメモリ計測と
   長時間・多数画像での測定が必要。共有可変状態の無保護な同時利用は導入しない。

全50実行・400画像で、保存バイト列、方式・遅延条件間の出力ハッシュ、独立した復元参照との画素ハッシュが一致した。
2/3/4スレッド方式では、全実行でそれぞれ2/3/4本の異なる変換スレッドと、その数の同時変換を確認した。
元の外部2ファイルのSHA-256も前回の記録と一致している。

## 制限

実サイト・実画像の計測ではない。入力8枚の小規模バッチであり、2/3/4ワーカーで仕事の分配数も異なる。
大量画像を連続処理した場合の温度・電力・キャッシュ増大や、複数章の状態管理は検証していない。
CPU周波数やOS上の他処理を固定していない。5回の範囲が重なる小さな差は確定的な優劣と扱わない。
0ms条件と100ms条件も別の時間帯に実行しており、両条件の絶対時間差を通信遅延の効果と解釈しない。

CPU使用率、各区間のGIL解放、メモリ使用量は未計測。PythonのWAT演算、Pillow、
1プロセスに集約されるコア検証、保存などの各寄与をこの実験だけで分離することはできない。
待ち時間の指標にはCPU競合とイベントループの再開待ちも混ざる。

インスタンスをワーカーごとに分ける方式は、inspect/requestで作った状態を変換へ引き継ぐ
一般的なプラグインにそのまま適用できる契約ではない。今回のtransformは合成metadataから必要情報を
取得できるため動作する。変換状態の受け渡し・並行安全性・キャンセル時の終了待ちを含む製品設計が必要。
